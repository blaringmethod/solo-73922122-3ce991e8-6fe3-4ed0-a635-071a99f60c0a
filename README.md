# 报警日志网关 · 双采集进程入仓 + 封存回收演示

模拟工厂网关把 JSONL 报警日志（设备号 / UTC 时间 / 报警码）写入共享目录，
两个独立采集进程持续把日志入仓到同一个 SQLite 检索库，并通过网页控制网关、
观察采集结果、**封存并回收已经采完的旧文件**。

重点演示：改名轮转、旧文件补写、并发采集、进程中断重启、**封存回收与崩溃恢复**
下的**不漏行、不重复、不误删新件**。

## 一、组件

| 组件 | 文件 | 职责 |
|---|---|---|
| 网页服务 | `app/main.py` | FastAPI：网关控制 + 入仓查询 + 封存/重试入口 + 后台回收线程 + 单页控制台 |
| 网关模拟器 | `app/gateway.py` | 追加 JSONL、写半行、改名轮转、按身份拒写已封存来源 |
| 采集器 | `app/collector.py` | 扫描共享目录与 `.reclaim/`，按来源身份与字节位点精确入仓（每容器一个进程，共两个） |
| 封存回收 | `app/reclaim.py` | 按身份封存、快照、后台等全部字节入仓后删除、失败重试、重启恢复 |
| 文件身份 | `app/fileid.py` | `statx` 出生时间 / xattr 令牌 + inode：改名不变、重建不复用 |
| 存储层 | `app/db.py` | SQLite（WAL），表结构、迁移、事务与并发连接 |
| 配置 | `app/config.py` | 全部参数走环境变量 |

## 二、不漏、不重、不错认来源

1. **身份与文件名、inode 复用解耦。** `file_id` 由 inode + 文件出生时间
   （`statx STATX_BTIME`，不可用时用 `user.alarm_source_id` xattr 令牌）组成。
   网关改名轮转后同一物理文件仍是同一身份；删掉后新建的文件即使复用旧路径或旧
   inode 编号，出生时间/令牌不同，就是**新身份**——从 0 字节开始采，旧位点不会
   被继承，两件数据不会混在一起。
2. **身份与数据取自同一个 fd。** 采集器打开文件后，用该 fd 计算身份、取大小、
   读内容；不再次 `stat` 路径，避免“scan 后路径被换掉”把新文件字节记到旧身份下。
3. **位点与数据同一事务。** `read_offset` 与新插入的行在同一个
   `BEGIN IMMEDIATE` 提交；读/写失败则回滚，位点不前进，下一轮重读。
   `UNIQUE(file_id, byte_offset)` + 事务内复查位点保证两个采集器不会重复入仓，
   同文不同行仍各占一行。
4. **只入完整行。** 只消费到最后一个换行；末尾半行留在磁盘等补齐，且**只阻塞
   自己**，其它文件（包括新建活动文件）照常推进。跨块读取支持超长单行；超过
   `MAX_LINE_BYTES` 仍无换行则挂起并报错，绝不静默截断。
5. **坏行只阻塞自身。** 解析失败时位点停在坏行起点、记录 `parse` 错误；修复后可
   继续入仓。
6. **旧库平滑升级。** 首版数据库（`file_id` 只有 inode）在启动时原地迁移为新的
   身份格式，已入仓明细与位点原样保留；源文件已消失的旧身份保持原样仍可查询。

## 三、轮转与三个名额

* 只做 `rename`：`alarms.jsonl → alarms.1.jsonl`，世代号顺延，随后创建同名空
  文件；**不删除、不截断**。
* 目录内最多 `MAX_GENERATIONS=3` 个名额（含当前件）。达到上限时轮转返回 409。
* **名额按“还在占用的来源身份”统计**：文件已封存但后台尚未真正删除时仍占名额；
  unlink 成功后名额立即释放，轮转恢复可用。

## 四、封存与回收

网页上每个非当前件都有「封存并回收」按钮。流程：

1. **按页面所见身份选择**。请求携带页面渲染时的 `file_id`（不是文件名）。
   若期间网关又改名轮转，仍会封存**同一物理文件**；若该路径/ inode 已被新件复用，
   请求被拒绝，绝不误封新件。
2. **封存 = 关闭写入 + 快照**。在网关写锁内：校验身份、记录快照大小/mtime，
   先把回收任务写入 `archive_jobs`（**先登记后改名**），再把源件无覆盖改名到
   `shared/.reclaim/`。快照包含封存前所有已成功补写的字节。
3. **所有追加入口按身份拒写**。封存登记提交后，即使改名尚未发生或进程崩溃，
   追加/半行/补换行都会被拒；即使有人用同一文件名新建了文件，新文件是新身份，
   旧身份仍然拒写。
4. **等全部字节入仓才删**。后台线程只有当 `read_offset` 覆盖封存文件当前全部
   字节、身份仍一致、大小未缩小时才 unlink。半行 / 坏行 / 变短时**保留源件**并在
   页面显示原因。
5. **删除失败可重试**。unlink 失败 → `delete_failed` + 退避自动重试 + 页面
   「重试回收」立即重试；源件仍在，名额不释放。**只有实际 unlink 成功后**才标记
   `done` 并释放名额。
6. **崩溃自动接续**。启动时恢复未完成任务：
   * 已登记未改名 → 按身份找回原件（即使已被轮转改名）再改名；
   * 已改名未删除 → 继续等待/删除；
   * 已 unlink 未记账 → 补记为 `done`。
   每一步都以“身份是否仍匹配”为前提；旧名被新件占用时任务结束为 `missing`，
   **不会删除或改写新件**。
7. **入仓明细与来源身份永久保留**。回收只删除源文件；`alarms` 行、`file_states`
   身份/位点/行数都保留，页面继续展示已回收来源及其状态。

采集器在封存过程中继续读取（`.reclaim/` 也在扫描范围内），所以“读取进行中封存”
不会丢字节；其他文件的追加、采集、查询在此期间照常进行。

## 五、运行

```bash
docker compose up --build
# 打开 http://localhost:8000
```

启动三个容器：`web`（FastAPI + 后台回收线程）、`collector-a`、`collector-b`，
共享两个卷：`shared_data`（JSONL 目录，含 `.reclaim/`）与 `db_data`（SQLite）。

网页功能：

* 追加完整记录 / 写半行 / 补换行 / 改名轮转；下拉框选中旧文件即可补写（写入按
  页面身份校验）。
* 文件表按 `file_id` 关联状态，展示 inode、大小、已提交位点、行数、位点状态、
  封存按钮、回收状态与**保留原因**；已回收来源仍列出其身份与入仓统计。
* 封存回收任务表：快照字节、当前位点、状态、原因、删除尝试次数、「重试回收」。
* 采集进程心跳、入仓记录（file_id / 行号 / 字节偏移 / 源路径 / 采集者）、采集错误。

## 六、HTTP 接口（详见 `/docs`）

网关：`POST /api/gateway/append`、`/fragment`、`/complete`、`/rotate`，
`GET /api/gateway/files`（含名额使用情况）
回收：`POST /api/reclaim/seal`（body `{"file_id": "..."}`）、
`POST /api/reclaim/retry/{job_id}`、`GET /api/reclaim/jobs`
查询：`GET /api/alarms`、`/api/file-states`、`/api/collectors`、
`/api/errors`、`/api/stats`
运维：`GET /healthz`
（`POST /__test/shutdown` 仅在 `ALLOW_TEST_SHUTDOWN=1` 时可用，生产镜像不开启）

## 七、自测

```bash
# 端到端：真实拉起 1 个 web + 2 个采集器进程
PYTHONPATH=. python3 -I tests/selftest.py
# 故障注入：写库失败不推进、读失败不推进、跨块读取、空行
PYTHONPATH=. python3 -I tests/test_faults.py
# 封存回收端到端：12 组场景
PYTHONPATH=. python3 -I tests/reclaim_test.py
# 身份与旧库迁移
PYTHONPATH=. python3 -I tests/identity_test.py
```

覆盖要点：

* `selftest.py`：基础入仓、改名轮转身份保持、旧文件补写、半行挂起不阻塞新文件、
  3 件上限拒绝且不删不截、并发 + 双采集器无漏无重、采集器中断重启、坏行只阻塞
  自身、字节偏移与源文件逐字节对应、同文不同行分别保留。
* `test_faults.py`：写库失败位点不前进、跨块读取、空行、读失败位点不前进。
* `reclaim_test.py`：
  R1 采完封存→删除且保留明细/身份、释放名额；R2 半行未入仓保留源件并显示原因，
  补齐后自动删除；R3 坏行保留源件并显示原因，修复后完成；R4 三个追加入口按身份
  拒写，同名新建文件不受影响；R5 封存前补写字节包含在快照内；R6 页面旧身份在轮转
  改名后仍封存原件；R7 复用路径的新件从 0 开始且不与旧来源混同；R8 删除失败保留
  源件与名额、重试后释放；R9 改名中断 / unlink 后记账中断 / 删除中断的恢复；R10 旧任务不删
  占用旧路径的新件；R11 封存期间其它文件继续追加/采集/查询，迟到读取仍入仓；
  R12 旧页面写入与旧页面封存请求都不会落到替换后的新件。
* `identity_test.py`：身份改名稳定、重建不同；旧格式数据库就地迁移保留行与位点；
  源文件消失的旧身份原样保留。

## 八、已知边界

* 出生时间依赖 `statx`；极老内核/文件系统不支持且不支持 user xattr 时退化为
  “仅 inode”，此时**inode 被回收复用**理论上可能无法区分。README 与代码
  注释均标注该退化；生产建议使用 ext4/xfs/btrfs 等提供出生时间或 xattr 的文件系统。
* 轮转世代号靠文件名约定；手工改名不影响身份，只影响世代排序。
* 封存后若外部进程（绕过网关）继续向 `.reclaim/` 内文件追加内容，回收会先要求
  把这些字节入仓再删除；若源件被外部截短则保留源件并报原因。
* SQLite 适合本演示规模与单机共享卷；更高吞吐可平移 Postgres，采集器“位点与数据
  同事务”的模型不变。
* 不处理外部截断活动文件（合同约定网关只追加/改名）；检测到变短会记录错误并
  冻结该文件位点，避免静默错位。
